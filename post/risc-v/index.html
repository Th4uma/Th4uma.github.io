知识结构

名词解释

进程调度

  • 进程：一个运行中的程序就是一个进程

  • 线程：

  • 调度：CPU在某段时间内快速切换运行多个进程，虽然CPU同一时刻只能运行一个进程，但由于切换的足够快，从而看起来是同时运行

  • 上下文：进程在某个时刻的完整状态，包含了寄存器栈指针等信息

  • 上下文切换：

  • 时间片：

  • clone

  • fork

  • PCB

  • 用户进程：在用户态运行的程序，使用的硬件资源由内核来分配，权限低

内存管理

  • 栈：存放函数调用相关的数据

  • 堆：程序运行过程中动态申请的内存区域

  • 虚拟内存：操作系统管理物理内存，为了防止信息泄露和安全问题，会给每个进程分配一块单独的专属内存，分配是通过虚拟地址来交给进程，这就是虚拟内存，而虚拟地址再通过页表映射到物理内存

  • 页表：虚拟内存对应物理内存的映射表，每个进程的页表都是独立的

CPU与硬件

  • 架构：CPU指令集和运行模式的整体设计结构，不同架构运行模式不同，指令不互通

  • 用户态：CPU运行普通程序的状态，很多权限受限，而且没有办法直接控制硬件

  • 内核态：CPU运行操作系统内核的状态，权限最高但没有办法直接由用户态控制

  • 寄存器：

  • trap：陷入，在遇到系统调用、中断、异常等操作的时候，CPU状态改变成内核态这个过程就是陷入

  • 异常：

  • 中断：

  • trapframe：CPU状态切换到内核态时，需要保存当前进程的上下文，这就是用来保存的结构体，切换回用户态时会将上下文取出用来恢复状态

  • 互斥：

系统调用

  • syscall：系统调用，用户态如果需要执行内核态权限的操作就需要它，由用户态陷入内核态进行
  • syscall 分发表：

程序构建

  • 交叉编译：在一种架构机器上将程序源文件编译成另一种架构的可执行文件
  • ELF：

流程描述

  • 系统启动流程：bootloader > kernel > 初始化内存与文件系统 > 创建第一个用户进程 > exec(init0) > 进入shell

  • 系统调用流程：用户程序调用 syscall > 参数与 syscall 编号写入寄存器 > trap > CPU 陷入内核态 > 保存上下文到 trapframe > 内核根据 syscall 编号找到对应处理函数 > 解析参数并执行系统调用 > 返回值写入寄存器 > 恢复上下文 > 返回用户态继续执行

基础与调试

QEMU

QEMU 是一个开源的模拟器与虚拟化工具，可以在一种架构的主机上模拟另一种架构的运行环境。既能模拟完整计算机硬件来运行操作系统，也能单独运行异构架构的用户程序

系统级模拟

类似真机模拟，它模拟的是整台计算机的硬件环境。操作系统会认为自己正在真实硬件上运行，这会让开发与调试更方便

  • -drive file=$(fs.img)：挂载文件系统镜像

int main() {

    // Create & Open file

    assert(n >= 0);

实战

启动系统后看到下面的输出，意思是系统最初的用户进程init0退出了，所以内核报错后停止

因此关键是找到最初的用户进程，根据提示找到src/kernel/proc.c，打开后搜索init0，可以看到

1
2
3
4
5

char *argv[] = {USER0, NULL};

if (exec(USER0, argv, envp) != 0) {
    panic(USER0 " load");
}

说明USER0决定第一个用户进程

在根目录查找USER0的定义

1

grep -R "define USER0" .

可以找到#define USER0 "masquerade"，这就是问题所在

正常情况下，系统启动时第一个运行的用户程序应该是#define USER0 "init0"，但现在被改成了masquerade，所以系统启动后实际执行了这个程序。它就是实验故意放进去的假程序，不会正常启动系统，而是输出提示然后退出

问题在于第一个用户进程是不能随便退出的。对于操作系统来说，kernel 虽然启动完成，但用户态环境还没有真正建立起来。第一个用户进程就像整个用户空间的根节点，一旦它退出，后面所有东西都没法继续运行。所以系统看到它退出就会直接停止运行，报错panic: init exiting

在 Linux 中也是一样，启动后会有一个最初的用户进程，一般是 init 或 systemd， PID 永远是 1。如果它异常退出，Linux 就会认为系统发生错误

第一个用户进程不能退出，否则系统将失去整个用户态环境

修复方法是编辑include/param.h这个文件，找到#define USER0 "masquerade"将masquerade改成init0

保存后重新编译，可以看到系统恢复正常

2

./run-qemu.sh

程序在内存中通过“栈”来管理函数调用。每次调用新函数时，CPU 就会在栈上压入当前函数的返回地址和旧的栈帧指针（FP），以此形成一个向后追溯的隐式链表。当 GDB 执行 backtrace 时，它会顺着当前函数的 FP 寄存器，逐层读取上级函数的 FP 和返回地址，从而在内存中还原出完整的函数调用链条

在编译时加上编译选项-g，

1

gcc hello.c -g -o hello

不加 -g 编译时，GDB 只能通过链表拿到一堆纯数字的内存地址；而加上 -g 编译选项后，编译器会在可执行文件中额外嵌入一张调试信息表（DWARF）。这张表记录了二进制内存地址与源代码的强对应关系（比如：地址 0x5184 对应 hello.c 的第 7 行，属于 foo 函数），GDB 检索该表后，就能把十六进制地址翻译成函数名和代码行号。

void backtrace() {
    uint64_t fp;

    // 读取当前 frame pointer（s0 / fp）
    asm volatile("mv %0, s0" : "=r"(fp));

    // 当前进程内核栈范围
    uint64_t bottom = (uint64_t)current->kstack;
    uint64_t top = bottom + KSTACK_SZ;

    kprintf("--- Backtrace Start ---\n");

    int depth = 0;

    // 顺着栈帧往上走
    while (fp >= bottom && fp < top) {

        // 防止栈损坏死循环
        if (depth++ > 32) break;

        // RISC-V 调用约定：
        // fp - 8  : return address (ra)
        // fp - 16 : previous fp
        uint64_t ra = *(uint64_t *)(fp - 8);
        uint64_t next_fp = *(uint64_t *)(fp - 16);

        kprintf("  0x%lx\n", ra);

        // 异常保护
        if (next_fp <= fp || next_fp == 0) {
            break;
        }

        fp = next_fp;
    }

    kprintf("--- Backtrace End ---\n");
}

原因是GDB运行在家目录，而文件在实验目录中。解决方法是进入实验目录再执行 GDB

在 proc.c 的 user0_init() 中加入 backtrace() 导致 panic: kerneltrap

  • 原因：在 user0_init() 执行期间，第一个用户进程还在创建阶段，其内核栈（kstack）和运行上下文还没有被完全构建完毕。此时强行进行栈回溯，由于没有合法的 fp 链，会导致指针解引用越界，触发内核异常页错误（Kernel Trap）。
  • 解决方法：切勿在进程未完全就绪的初始化函数中执行栈回溯。

设置了精确过滤条件（如 if (p && p->pid > 2 && num == 1) { backtrace(); }）导致完全不打印

  • 原因：硬编码了硬性的系统调用号（如 num == 1），但在不同的操作系统实现或动态生成的头文件（syscall_gen.h）中，fork 或 clone 的系统调用号并不一定是 1。条件未能命中，导致测试桩失效。
  • 解决方法：不猜测具体的数字，改用内核自带的宏定义（如 #ifdef SYS_fork）或通过字符串匹配函数（如 strcmp(syscall_name(num), "fork") == 0）进行精准 Hook 拦截。

内核刚开机就无限循环爆出 --- Backtrace Start --- 和 --- Backtrace End ---：

  • 把 backtrace() 挂到 myproc() 内部导致全系统炸裂

  • 解决方法：从打印模块中彻底删除测试桩，将 backtrace() 移至系统调用入口 src/kernel/syscall.c 中。

  • 内核在开机引导和终端加载时，其打印和环境初始化底层频繁使用了 write 等系统调用。只要将测试桩无差别地丢在 syscall() 函数中，开机时每一个字符或每一次行为都会高频触发回溯。

系统调用

用户程序没有权限直接访问内核，只能通过 syscall 对内核执行操作。系统调用也就是用户态通过ecall陷入内核，内核根据syscall号调用对应函数，然后返回结果

#include "common.h"
#include "mm/vm.h"
#include "kernel/syscall.h"
#include "printf.h"

uint64_t sys_echo() {
    // 用户态传入的字符串地址
    uint64_t user_ptr;
    int len;
    char buf[128];
    
	// 从 syscall 参数里取参数
    if (argaddr(0, &user_ptr) < 0 || argint(1, &len) < 0) {
        return -1;
    }
    
	// 防止溢出
    if (len < 0 || len > 127)
        len = 127;
    
	// 从用户虚拟地址复制数据到内核
    if (copy_from_user(buf, user_ptr, len) < 0) {
        return -1;
    }
    
	// 手动添加字符串结束符
    buf[len] = '\0';
    
	// 内核打印字符串，这里不是用户内存，是内核自己的 buf
    printf("%s\n", buf);
    
	// 返回用户态
    return 0;
}

可以看到这里的函数uint64_t sys_echo()并没有参数，这是因为系统调用和普通的用户态程序不一样

  • 用户态程序实现函数的过程是先把参数的值存进寄存器，跳转到函数执行，这时候再从寄存器取出值
  • 系统调用是在用户执行syscall后，参数被放入寄存器，在CPU 陷入内核时，这些寄存器内容也就是上下文会被保存到trapframe里用于之后恢复进程。argaddr(0, &user_ptr)就是在从这里取出第0个参数解析成地址，argint(1, &len)就是取出第一个参数解析成int。在系统调用完成后，返回值被存入寄存器，用户态寄存器恢复，CPU回到用户态。syscall本质上是带有参数的trap

在内核态无法直接访问用户态的指针，因为用户页表和内核页表不一样，用户传入的是虚拟地址，这时候就要用到copy_from_user()来拷贝内存

void syscall(void) {
    struct proc *p = current;
    int num = proc_get_tf(p)->a7; 

    if (num > 0 && num < NELEM(syscalls) && syscalls[num]) {
        uint64_t ret = syscalls[num]();
        proc_get_tf(p)->a0 = ret; // 写入返回值
        
        //拦截并打印 trace 信息
        if (p->traced_syscall == num) {
            // 使用系统提供的 syscall_name 获取字符串名称
            kprintf("trace: PID %d calls %s\n", p->pid, syscall_name(num));
        }
        
    } else {
        kprintf("PID %d %s: unknown sys call %d\n", p->pid, p->name, num);
        proc_get_tf(p)->a0 = -1;
    }
}

}

踩坑记录（半整理）

printf报错implicit declaration of function 'printf'和stdio.h: No such file or directory：

分别是最开始没有添加头文件，和第二次加入#include <stdio.h>产生的报错。原因是内核不是普通 Linux 用户程序，没有标准 C 库环境，不能直接使用 libc。解决方法是用内核自己的头文件#include "printf.h"

sys_echo报错undefined reference to 'syscall'：

原因是用户态代码里调用了 syscall()，但工程里根本没有这个函数的实现，也没有链接到任何提供它的库，所以链接阶段直接报 undefined reference。

在这个实验环境里，用户态通常不会提供完整的 libc，也不会默认有 syscall() 这种通用封装函数，所以直接写 syscall(...) 会导致链接失败。

解决方式就是绕开这一层封装，直接用 RISC-V 的 ecall 指令发起系统调用，把参数放进约定寄存器里，比如 a7 放系统调用号，a0 放参数。这样就不依赖任何外部函数。

可以在 init0.c 里加一个内联函数，把 trace 直接包装成 ecall 调用

copy_from_user 参数类型错误，报错passing argument 2 of 'copy_from_user' makes integer from pointer without a cast：

原因是把用户态的 char * 指针直接传给了 copy_from_user，但正常情况下传的应该是用户地址的数值形式。用户态指针在内核里只是一个虚拟地址标记，不能直接当普通指针用。应该先用 argaddr 把参数取成 uint64_t 地址

1
2

uint64_t addr;
argaddr(0, &addr);

然后再调用copy_from_user(buf, addr, len);也就是先把用户指针转成内核能理解的地址数值，内核再把数据从用户空间拷贝到内核空间

编译完成后报错panic: init exiting：

原因是init0.c写错导致第一个用户进程退出，之后的用户进程无法启动，最终系统崩掉，解决方法是排查init0.c，保证逻辑完整
